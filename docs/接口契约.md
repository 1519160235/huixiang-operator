# 接口契约

> **骨架阶段未实现，仅作实现依据。** 下面是从四源深读结论整理出的中文对照表。现在没有签名客户端、没有凭据、没有发布层，不连真实 API。将来写发布层时逐条对照，不靠猜。
> 本表已按四源融合结论修正旧文档错误（`topicIds` 类型、图床尺寸、签名分流）。

## 一、分区与分类

| 项 | 口径 | 错了会怎样 |
|---|---|---|
| 图文帖 `link_tag` | `27` | 给错值发不出去 |
| 动态（无图）`link_tag` | `28` | 纯文字帖该用这个 |
| 文章 `link_tag` | `11` | 长文走 HTML 正文 |
| `21` | 不是合法发帖分类 | 小黑盒判「错误的动态分区」直接拒 |
| `topicIds` | 逗号分隔的数字字符串，如 `"12,34,56"`，**不是 int 数组** | 传数组或单个 int 会解析失败 |
| 活动话题 | 走 `hashtags` 参数，传准确名称；有奖励活动话题优先 | 名字过期就白丢一次曝光 |
| 话题数量 | 最多 5 个 | 超过 5 个可能被拒 |

## 二、字段口径

| 字段 | 口径 | 错了会怎样 |
|---|---|---|
| 推荐流帖子 ID | `postId`，不是 `id` | 取到空值，后面全链路断 |
| 完整正文 | `link.text`，块序列化 JSON | `description` 只是摘要，拿摘要改正文会把内容改没 |
| 图片 | 在正文 `text` 的 `img` 块里 | 当成单独字段去找会找不到 |
| 分区解析 | 名称按准确匹配换成数字 topic ID | 名字差一个空格就解析不到 |
| 标题读回 | 可能有短暂延迟 | 别因此重复提交 |

## 三、签名与域名

| 项 | 口径 |
|---|---|
| 读请求（GET） | 走 `api.xiaoheihe.cn`，签名用 `generate_hkey(path, stamp, nonce)` |
| 写请求（POST） | 用 `comment_query`，hkey 用 `stamp+1` 计算 |
| 写域名 | workshopapi 域名 |
| 读域名 | api 域名 |
| hkey | 每次请求按路径重新算，不能把一条请求的签名复用到别的路径 |
| 客户端契约 | 不等于稳定公开 API，平台可能改；改了先改本表再改代码 |

关键区分：读和写的 hkey 算法口径不同。读是 `generate_hkey(path, stamp, nonce)`；写是 `comment_query` 那套，hkey 用 `stamp+1`。别把两套混用。

### 平台变更记录：2026-11-11 起写接口签名升级到 `_rnd` v16

> 2026-11-12 1.0.6 更正：此前写的「web 写端点整体停用」是误判，以本节为准。
> 依据为线上前端 `index-C10NdQWW.js` 的真实请求实现（`_n.defaults.rnd="16"`）。

**写请求 q 参数**（与线上前端一致）

| 字段 | 值 / 算法 |
|---|---|
| `hkey` | `Tr(path, stamp+1, nonce)`：字符集映射 + 交错 + MD5，尾部 6 字节全参与校验和 |
| `_time` / `nonce` | `stamp`（原始时间）/ 32 位大写 hex |
| `_rnd` v16 | `"16:" + base64url(iv ‖ AES-256-GCM(ct+tag))`，无 padding |
| v16 密钥 | 前端公开的 `HFFSTsqmvG3uGxPNXDQW+1VARfqgG4nT6LS1PX7F8NQ=`（32 字节） |
| v16 AAD | `heybox-rnd:v16`；IV 12 字节随机 |
| v16 明文 | `JSON.stringify(["<time>","<nonce>","<path>/"])`，路径必须带尾斜杠 |
| v15（旧） | `"15:" + HMAC-SHA256(WORKSHOP_KEY, …)`，已被平台判为验签失败 |
| 平台参数 | `heybox_id` / `web_version` / `x_app=heybox_website` / `client_type=web` 等 |

**真机响应对照**（无效 link_id + 空 text，不会真发评论）

| 请求 | 平台响应 |
|---|---|
| v15 `_rnd` | `评论功能暂不可用` |
| v16 正确签名 | `你的账号无法使用该功能，如有疑问请前往设置-帮助中心&问题反馈` |
| v16 篡改 `_rnd` / 错误密钥 | `评论功能暂不可用`（验签失败） |
| v16 去掉 `_rnd` | `缺失参数` |
| v16 篡改 / 去掉 hkey | `非法请求` / `缺少必要参数[hkey]` |

**结论**：端点活着，v16 签名被正常接受。正确签名后仍回「你的账号无法使用该功能」，
且与 cookies、真实风控 token（`x_xhh_tokenid`，B 开头 89 字符）、出口 IP、
`heybox_id` / 设备参数 / UA 全部无关；`post_comment_permission` 仍为 1。
这是账号在 **web 通道**的定向写功能限制，App 端不受影响（用户实测 App 可评论）。
重新扫码登录无效（不带 cookies 结果相同）。

**1.0.8 起**：该限制已解除（同一个 web 探针重新回到业务层校验），
评论 / 发帖默认改回 web v16 签名；App 通道降级为兜底，只在 web 再次被
账号级限制、且本地抓包签名仍在有效期（≤4 分钟）时启用。

`/bbs/app/api/get/forbid_reason` 返回平台预设的封禁原因枚举（含「低质AI生成」
「AI生成内容问题」「水军相关」），不代表账号当前命中了其中某条。

## 四、图床 COS 三步

| 步 | 动作 | 要点 |
|---|---|---|
| 1 | `info/v2` | 传 `file_infos`、`scope=bbs`、`need_cache`，拿 bucket、region、对象 key |
| 2 | `token/v2` | 传 `bucket`、`keys`、`mimetypes`、`is_multipart_upload`；临时凭据只在内存里用，不写文件、不写接口结果 |
| 3 | `PUT` → `callback/v2` | 先 PUT 到 COS，再查 `callback/v2` 的 `is_finished=true`，读 `preview_urls` / `thumbs` |

图片上限：

| 项 | 上限 |
|---|---|
| 单图大小 | ≤ 5 MB（旧文档写的 5 GiB 是错的） |
| 单图像素 | ≤ 2000 万像素 |
| 单帖图数 | 最多 6 张 |

平台可能转换 CDN 地址和 HTML 属性顺序，回读按同一资源标识与正文语义核验，不做 URL 字符串相等比较。

## 五、发帖与回读核验

| 项 | 口径 |
|---|---|
| 验证发帖 | 用 `get_post(postId)` / `fetch_thread_context` 回读 |
| `search_posts` | 不索引新帖。搜不到不能当作「没发出去」 |
| 接受但回读失败 | 记 `accepted=true, verified=false` |
| 没有服务端响应 | 结果未知，不自动重发 |
| 图片核验 | 只有附图真成功才要求回读含图；生图或上传失败就降级纯文字 |

## 六、评论与楼中楼

| 项 | 口径 |
|---|---|
| 回楼中楼 | 必须带 `rootId`，取通知的 `rootCommentId` |
| 顶层评论 | `reply_id` / `root_id` 两个都是 `-1` |
| 不带或带错 `rootId` | 上游返回 `error root` |
| 楼中楼分页 | 用 `root_comment_id` / `lastval`，`lastval` 取最后一条已读评论的 ID |

## 七、登录凭据

四个必需字段，缺一不可：

| 字段 |
|---|
| `user_pkey` |
| `user_heybox_id` |
| `heybox_id` |
| `x_xhh_tokenid` |

二维码有效期约 60~120 秒，过期重新触发即可。凭据只放数据目录，不写日志、不进 Git。

## 八、分区动态

| 项 | 口径 |
|---|---|
| 接口 | `TOPIC_INDEX` → `parse_catalog`，或 `searchEditorTopics` |
| 拉取方式 | 运行时动态拉取，定时刷新保证最新，不硬编码 |
| 签名 | 拉目录要带 hkey，不能用纯 cookie 手拼 URL |
| 失败处理 | 解析不到准确名称就跳过本轮，不往不确定的分区发 |
| 特殊参数 | 目录接口不带规定参数会报「请升级至最新版本」 |

## 十一、App 端写通道（1.0.7 引入，1.0.8 起仅作兜底）

取证方式：雷电模拟器装官方 `heybox-release.apk`（v1.3.401 / build 1151，
Android 9），ROOT 后用 bind mount 把 mitmproxy CA 装进系统证书区，
全局代理指向宿主机，抓到 HTTPS 明文请求。写请求由代理拦截并伪造响应，
**没有真的发出评论 / 帖子**（发帖探测时曾有 2 条空测试帖误发，已用
`/bbs/app/link/delete` 删除，返回 `status: ok`）。

| 项 | web 通道 | App 通道 |
|---|---|---|
| 参数组 | `x_app=heybox_website` / `client_type=web` / `web_version` | `x_app=heybox` / `x_client_type=mobile` / `os_type=Android` / `imei` / `build` / `dw` / `channel` / `time_zone` |
| `hkey` | 8 位字符集映射串（如 `U1V1I44`） | 8 位十六进制整数，无前导零（如 `E2AF3D9`） |
| `nonce` | 32 位大写 hex | 32 位混合大小写字母数字 |
| `_rnd` | `16:` + AES-GCM 密文，必填 | `14:` + 8 位 hex，**实测可删可改** |
| Cookie | `user_pkey` / `heybox_id` / 风控 token | `pkey` + `x_xhh_tokenid`，**必需**（缺了回「请重新登录」） |
| UA / Referer | Chrome / `www.xiaoheihe.cn` | `ApiMaxJia/1.0` / `http://api.maxjia.com/` |
| 写限制 | 「你的账号无法使用该功能」 | 无，正常进入业务层 |

**签名绑定范围**（真机消融，全部用不存在的 link_id + 空文本）：

| 改动 | 结果 |
|---|---|
| 改 `nonce` / `index` / 删 `h_src` / 改或删 `_rnd` | 仍通过验签 |
| 改 `heybox_id` / 换 web 参数组 | `非法请求` |
| 改 `_time` 或 `hkey` | `非法请求` / `验证参数错误` |
| 固定抓包时的 `_time` + `hkey`，换 IP 重放 | **只在 5 分钟内**通过，超时回 `请求失败了` |

结论：`hkey` 绑定 `path` + `heybox_id` + `_time` + 设备/版本参数，
**不绑定 body**，但服务端校验 `_time` 新鲜度：2026-11-12 18:22 实测
88 / 148 / 209 / 269 秒仍通过，329 秒起稳定失败，即 **TTL ≈ 300 秒**。
所以固化签名只能在抓包后几分钟内救急，长时间无人值守必须实时生成签名
（App 内 native 算法，尚未逆向）。`app_protocol.is_fresh()` 就是这道守卫，
默认安全线 240 秒，过期直接报错而不是硬发。

**表单口径**（`app_protocol.convert_form`）

| 接口 | form |
|---|---|
| 评论 `/bbs/app/comment/create` | `link_id` / `text` / `imgs` / `is_cy`，回复时加 `reply_id`、`root_id` |
| 发帖 `/bbs/app/api/link/post` | `draft=0` / `topic_ids` / `link_tag` / `text`(JSON 段数组) / `title` / `desc` |

**维护**：签名与账号 `34182985`、App 1.3.401、设备指纹绑定，且只有 5 分钟寿命。
换账号 / 平台换校验规则后需重新抓包，更新 `app_protocol.py` 的 `_RAW_QUERIES`。失效时服务端回
`验证参数错误` / `非法请求` / `请求失败了`（过期），熔断会拦住并停止生图。

**1.0.9 补齐的两块**：`app_pairs.json` 外部签名对 + Cookie 透传。

- 外部文件格式：`{"comment": {"query": "<整条 query>", "hkey": "...", "_time": "...", "cookie": "pkey=...;x_xhh_tokenid=..."}}`。
  只给 `hkey`/`_time` 不够——`h_src` / `index` 也是那次请求的一部分，拼旧模板会回「请重新登录」。
- 插件读取顺序：外部文件（按 mtime 热加载）优先，其次内置抓包值；
  `is_fresh()` 超过 240 秒直接判过期，不会硬发。
- 现场签名工具见工作区 `sign_farm.py`：模拟器里点一次发送、代理拦下、
  取整条 query 与 Cookie 写入 `app_pairs.json`，`--push` 直接上传服务器，
  `--loop N --interval 180` 可定时刷新（签名 300 秒到期）。
- **部署前提（重要）**：`sign_farm.py` 必须跑在装着模拟器 + mitmproxy 的机器上
  （当前是开发用的那台 Windows），**不能跑在 MaiBot 服务器上**——服务器是 KVM 虚拟机，
  没有嵌套虚拟化，也跑不动安卓模拟器。服务器侧只消费 `app_pairs.json` 这个文本文件。
  因此 App 兜底的实际可用范围 = 「那台机器开着 + 农场在跑」。
  **定位：人工应急工具，不是 7×24 兜底。** 开发机不常开，服务器也不会自己签；
  平台再次限制 web 写时，正确动作是「人工介入 → 起农场 → 续签 → 重试」，
  而不是指望它自动恢复。真要让服务器自给自足，只有两条路：
  逆向 `libapp.so` 的 `hkey` 生成逻辑，或用云手机常驻。

**1.0.8 的取舍**：固化签名撑不起 7×24 自动发布（每 5 分钟就得重抓一次），
而 web 写限制已解除，所以默认回到 web 通道；App 通道留作平台再次限制时的
兜底与取证工具。若要长期跑 App 通道，下一步是逆向 `libapp.so` 里的
`hkey` 生成逻辑（已确认 `_rnd` 不参与验签、`hkey` 与 `_time` 必须成对），
或在本地做「签名农场」按需刷新签名对。
