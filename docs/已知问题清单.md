# 已知问题清单

逐条按「问题 → 表现 → 根因 → 规避方式」记录。前 16 条来自历史实践，第 17 条起为四源融合阶段阅读源码后补充。全部为实测结论，非推测。

### 1. `link_tag` 21 非法，动态该用 28

- 问题：纯文字帖给了 21。
- 表现：小黑盒返回「错误的动态分区 failed」，帖子发不出去。
- 根因：21 根本不是合法发帖分类。合法值只有图文 27、动态（无图）28、文章 11。历史上有人把「无图动态」写成 21。
- 规避方式：有图 27、无图 28，在发布层一处定死，不再写 `else 21`。

### 2. 社区名硬编码过期

- 问题：白名单和默认值硬编码成「PC 游戏」。
- 表现：选了必然解析失败，发不出去。
- 根因：真实名字是「PC游戏」，没有空格；硬编码的名单本来就不全，也没有话题。
- 规避方式：分区和话题运行时拉取目录，按准确名称解析成数字 ID；解析不到就跳过本轮。

### 3. `dryRun` 占掉真实额度

- 问题：演练分支也写了 `post_gap.json`。
- 表现：演练一次，接下来 30 分钟的真发帖额度被占掉，连着三次把自己挡住。
- 根因：演练和真实共用一份额度状态，没隔离。
- 规避方式：`dryRun` 直接返回，不算额度、不写状态文件、不上传图、不发请求。

### 4. `postId` 写成 `id`

- 问题：从推荐流取帖子 ID 用了 `id`。
- 表现：拿到空值，后面读详情、回评论全断。
- 根因：字段名和直觉不一致，推荐流返回的是 `postId`。
- 规避方式：字段口径照 `接口契约.md`，取 `postId`，不靠猜。

### 5. 图片核验做错

- 问题：拿 `description` 或图片 URL 字符串相等去判断发没发成功。
- 表现：回读判成失败，或把没图的帖子误判成成功。
- 根因：正文 `text` 是块序列化 JSON，图片在 `img` 块里；`description` 只是摘要；平台还会转 CDN 地址和 HTML 属性顺序。
- 规避方式：按同一资源标识与正文语义核验；只有附图真成功才要求回读含图；生图或上传失败就降级纯文字，不换请求号重画。

### 6. `search_posts` 不索引新帖

- 问题：发完用搜索标题验证。
- 表现：已知存在的帖子，搜索返回 0 条，误以为没发出去。
- 根因：搜索不索引刚发的帖。
- 规避方式：验证一律用 `get_post(postId)` / `fetch_thread_context`。

### 7. 楼中楼 `error root`

- 问题：回楼中楼时把 `rootId` 直接赋成 `commentId` 本身。
- 表现：上游返回 `status=failed error root`。
- 根因：等于假设「要回的就是楼顶」，真实根评论是通知里的 `rootCommentId`。
- 规避方式：回楼中楼必带 `rootId`，取通知的 `rootCommentId`；顶层评论才用 `-1`。

### 8. 凭据缺字段、二维码过期

- 问题：登录态只存了部分 cookie；二维码放着等太久。
- 表现：请求鉴权失败；扫码提示已过期。
- 根因：四个必需字段缺一不可：`user_pkey`、`user_heybox_id`、`heybox_id`、`x_xhh_tokenid`；二维码有效期约 60~120 秒。
- 规避方式：四字段齐全才继续，过期就重新生成二维码；凭据只放数据目录，不写日志、不进 Git。

### 9. 残留旧 `config.toml` 版本不匹配

- 问题：目录里留着上一版配置文件，直接拿来跑新代码。
- 表现：字段读不到、默认值不对、插件组件为 0。
- 根因：`config_version` 与字段结构和新代码对不上，平铺字段读不到。
- 规避方式：新仓库、新插件 ID，配置从零生成；升级前先备份，`config_version` 与代码对齐；不复用旧文件。

### 10. `[plugin]` 段位置导致顶层配置读不到

- 问题：把 `[plugin]` 段写在配置文件最前面。
- 表现：顶层配置读不到，插件组件为 0。
- 根因：TOML 里表头之后的键都归这张表，直到下一个表头。放最前面会把后面的顶层键吞进 `[plugin]`。
- 规避方式：`[plugin]` 放最后，段里带 `config_version`；配置模型按 TOML 分段嵌套。

### 11. 插件契约四件套

- 问题：工厂函数、类属性名、`[plugin]` 段、首次装依赖，四样里少一样。
- 表现：`当前插件未声明 config_model`、`配置错误，仅加载配置管理`、`缺少 create_plugin 工厂函数`、组件 0；首次启动报 `connect_and_handshake timeout=10.0` 退出码 1。
- 根因：要有模块级 `create_plugin()`、类属性 `config_model = XxxConfig`、`[plugin]` 段含 `config_version`、配置模型分段嵌套；首次启动装 Python 依赖卡住主循环，超过硬编码 10 秒握手超时，且不自动重试。
- 规避方式：四样一次配齐；装完带依赖的插件再启动一次就好，不要误判为崩溃去回滚。

### 12. Windows 编码

- 问题：用 PowerShell 5.1 写中文，或控制台按默认编码打印。
- 表现：中文变 `?`；`'gbk' codec can't encode character '\u2713'` 直接崩。
- 根因：`Set-Content` / `Invoke-WebRequest -Body` 不是 utf-8，控制台默认 GBK。
- 规避方式：改文件一律 Python 并写 `encoding="utf-8"`；启动设 `PYTHONUTF8=1`、`PYTHONIOENCODING=utf-8`；远程脚本保持纯 ASCII。

### 13. 插件日志在 stderr

- 问题：翻 `app_*.jsonl` 找插件日志。
- 表现：找不到，误以为插件没跑。
- 根因：插件的 logger 输出在 stderr，前缀是插件 ID；`app_*.jsonl` 是主程序日志。
- 规避方式：按插件 ID 过滤 stderr 日志；主程序日志和插件日志分两处看。

### 14. 改 `model_config.toml` 必须重启

- 问题：改完模型配置直接看效果。
- 表现：日志里还是旧值。
- 根因：`bot_config.toml` 会热载，`model_config.toml` 不会。
- 规避方式：改完 `model_config.toml` 必须重启；重启前确认没有内存态长任务在跑。

### 15. 按 PID 杀进程，别 `taskkill node.exe`

- 问题：按进程名统一杀 node。
- 表现：把别的 node 服务一起杀掉，或把 tsx 父子进程当成两个实例误删。
- 根因：多个服务都叫 `node.exe`，进程名不是唯一标识。
- 规避方式：按命令行匹配到具体进程，再按 PID 精确停，一次只处理目标。

### 16. WebUI API 只收 POST，路径末尾不带斜杠

- 问题：用 GET 调运行时接口，或路径末尾多写一个斜杠。
- 表现：404。
- 根因：运行时接口只收 POST，`kind` 只能是 `queries` / `actions`，路径末尾带斜杠不匹配。
- 规避方式：一律 POST，路径末尾不带斜杠；`kind` 只用这两个值。

### 17. `topicIds` 是数字字符串，不是 int 数组

- 问题：旧文档把 `topicIds` 写成「int 数组」。
- 表现：按数组组装 payload，发帖被拒或话题不生效。
- 根因：真实口径是逗号分隔的数字字符串，如 `"12,34,56"`。
- 规避方式：`接口契约.md` 已改；代码里用字符串拼接，最多 5 个话题，不做数组序列化。

### 18. 读、写两套签名不能混用

- 问题：把读请求的 hkey 算法套到写请求上。
- 表现：写接口鉴权失败。
- 根因：读 GET 走 `generate_hkey(path, stamp, nonce)`；写 POST 用 `comment_query`，hkey 用 `stamp+1`。两套口径不同。
- 规避方式：签名分流硬编码在发布层两处，读一套、写一套，不共用。

### 19. 图床尺寸上限写错

- 问题：旧文档把单对象上限写成 5 GiB。
- 表现：超大图传上去被 COS 拒。
- 根因：真实上限是单图 ≤5 MB、≤2000 万像素、单帖最多 6 张。
- 规避方式：`media_upload.py` 的 `parse_image` 在生成前就校验尺寸和数量，不达标直接降级。

### 20. 去 AI 味阈值两档，不使用一个值

- 问题：评论和正文用同一个 AI 味阈值。
- 表现：评论过严拦太多，或正文过松放走机器腔。
- 根因：评论短、正文长，阈值本就不同：评论 45、正文 60。
- 规避方式：护栏层按内容类型取阈值，两档分开配。

### 21. 限流要双指标

- 问题：只限间隔不限总量，或只限总量不限间隔。
- 表现：短时间狂发，或一天总量爆掉。
- 根因：限流是双指标：单请求 5 秒、每小时 30 次。
- 规避方式：`rate_limiter.py` 同时记「上次请求时间」和「小时计数」，两个都过才放行。

### 22. 验证码熔断要有冷却时长

- 问题：遇到验证码只是「这次停」，下次继续硬撞。
- 表现：连环失败。
- 根因：验证码出现后要冷却 5 分钟，冷却期内一律不放行。
- 规避方式：熔断状态持久化，带 5 分钟冷却，重启后不丢。

### 23. 按「想象的 SDK」写插件入口，六处全错

- 问题：入口照记忆里的写法来：`from maibot_sdk import MaiBotPlugin` 然后 `def __init__(self, config=None, ctx=None)`、`self.config = config`、`self.ctx = ctx`、`def on_load(self)` 同步方法、`create_plugin(config=None, ctx=None)`。
- 表现：插件装上就加载失败：`TypeError: __init__() got an unexpected keyword argument 'config'`、`AttributeError: property 'config' has no setter`、`TypeError: object NoneType can't be used in 'await' expression`；或者组件数为 0。
- 根因：真实契约（2026-11-04 在部署环境逐条实测核对，SDK 2.21.0）是：
  1. `create_plugin()` **必须无参**，宿主不会传 config / ctx 进来；
  2. 主类 `__init__(self)` 调 `super().__init__()`，**无参**；
  3. `self.config` 是基类**只读 property**，配置靠 `set_plugin_config(dict)` 注入，不能赋值；
  4. `self.ctx` 也是只读 property，靠 `_set_context(ctx)` 注入；
  5. `on_load` / `on_unload` / `on_config_update(scope, config_data, version)` **必须 async**，缺一个基类抛 `NotImplementedError`；
  6. 组件用 `@Command(name, description, pattern=...)` / `@Tool(name, brief_description=...)` 装饰器声明，不是自己维护一份 `COMMANDS` 字典再「打算以后注册」。
- 规避方式：`tests/test_sdk_contract.py` 用真实 `maibot_sdk` 逐条断言这六点；本地没有 SDK 时整份 skip，有 SDK 时必须全过。改入口前先跑它。

### 24. `[plugin].config_version` 只写在 config.toml 里不够

- 问题：配置模型不定义 `plugin` 段，只在 `config.toml` 里写了 `[plugin] config_version = "1.0.0"`。
- 表现：`PluginConfigVersionError: 插件配置文件缺少 [plugin] 配置节，且必须提供 plugin.config_version 版本号`，插件在**生成默认配置**这一步就挂了，连 `on_load` 都进不去。
- 根因：SDK 的 `build_plugin_default_config()` 先用**配置模型**生成默认配置，再立刻 `extract_plugin_config_version(default_config)`；模型里没有 `plugin` 段，默认配置里就没有。
- 规避方式：配置模型里必须有 `class PluginSection(PluginConfigBase)` 且顶层 `plugin: PluginSection = Field(default_factory=PluginSection)`；`config.toml` 里那份仍然要有，且放最后（两份都要，作用不同）。

### 25. 配置模型里不能写 `from __future__ import annotations`

- 问题：为了类型注解方便，在 `config_model.py` 顶部加了 `from __future__ import annotations`。
- 表现：pydantic 解析字段类型失败，配置模型建不起来，插件加载失败。
- 根因：开了延迟注解后，pydantic 拿到的是字符串而不是真实类型；SDK 的配置模型是 pydantic BaseModel。
- 规避方式：`config_model.py` 和 `plugin.py` 都不写这一行；需要 `X | None` 之类写法就直接用（Python 3.10+ 原生支持）。

### 26. 业务层不能依赖插件入口

- 问题：把 `_StateContainer` 放在 `plugin.py`，测试和 layers 都 `import plugin` 拿它。
- 表现：本地没装 `maibot_sdk` 时，146 个纯逻辑测试里 41 个直接崩在 `ModuleNotFoundError: No module named 'maibot_sdk'`——明明测的是业务逻辑，却被入口的 SDK 依赖拖死。
- 根因：`plugin.py` 必须 `from maibot_sdk import ...`，而业务层不该知道宿主长什么样。
- 规避方式：状态容器放 `state.StoreContainer`（零第三方依赖），配置读取统一收在 `layers/_cfg.py`，业务层只认薄上下文（`.config` / `.paths` / `.store` / `.api` / `.generate_text`）。这样没装 SDK 也能跑全部业务测试（159 项里只 skip 掉 22 项宿主相关）。

### 27. manifest 不能写 `keywords` / `notes`

- 问题：manifest 里加了 `keywords`（关键词）和 `notes`（备注），觉得很合理。
- 表现：`Manifest 校验失败 [local.huixiang-operator]: 存在未声明字段: keywords; 存在未声明字段: notes`，
  插件直接注册失败。
- 根因：`PluginManifest` 是 pydantic 严格模型（`extra="forbid"`），只允许 17 个字段：
  `manifest_version` / `version` / `name` / `description` / `author` / `license` / `urls` /
  `host_application` / `sdk` / `dependencies` / `llm_providers` / `capabilities` / `i18n` /
  `id` / `plugin_type` / `display` / `changelog`。多一个都不行。
- 规避方式：写完 manifest 数一遍字段名，只留白名单里的。

### 28. 插件目录不会被加进 `sys.path`

- 问题：`plugin.py` 里直接 `import contracts` / `from layers import ...`，本地跑得好好的。
- 表现：`加载插件失败 [local.huixiang-operator]: No module named 'contracts'`。
- 根因：Runner 用 `importlib.util.spec_from_file_location` 按**文件路径**加载，模块名是扁平的 `plugin`，
  **不会**把插件目录写入 `sys.path`。本地能跑是因为测试脚本自己加过路径。
- 规避方式：`plugin.py` 顶部（所有包内 import 之前）做路径自举：
  ```python
  import sys
  from pathlib import Path
  _PLUGIN_ROOT = Path(__file__).resolve().parent
  if str(_PLUGIN_ROOT) not in sys.path:
      sys.path.insert(0, str(_PLUGIN_ROOT))
  ```
  另一个选择是 `try: from .x import ...  except ImportError: from x import ...`（better-diary 的写法），
  两条路都要能走通。

### 29. `config_reload_subscriptions` 只认 `bot` / `model`

- 问题：写了 `config_reload_subscriptions = ("self",)`，想订阅自己的配置变更。
- 表现：`加载插件失败: 不支持的配置热重载订阅: self`。
- 根因：`normalize_config_reload_subscription()` 的别名表只有 `bot` / `model` 两项，
  `CONFIG_RELOAD_SCOPE_SELF = "self"` 是 `on_config_update` 的 scope 值，**不是**可订阅项。
- 规避方式：不订阅就不写这个类属性（基类默认空）；要订阅只能写 `("bot",)` / `("model",)`。

### 30. 命令 `return (True, 文本, 2)` 不会自动发出去

- 问题：命令方法返回三元组，以为宿主会把它发到聊天。
- 表现：日志里 `命令执行成功: hx_status (拦截等级: 1)`、`命令处理完成...: 回响状态（...）` 全都正常，
  但用户那头**一个字都收不到**，看起来像「命令没响应」。
- 根因：三元组只是「处理结果报告」，宿主拿它写日志、决定是否跳过后续消息处理，
  **不负责发送**。发消息必须插件自己调 `self.ctx.send.text(text, stream_id)`。
- 规避方式：写一个 `auto_reply` 装饰器统一补发送，别逐条命令手写（漏一条就等于那条命令无输出）：
  ```python
  @Command(...)      # 上
  @auto_reply        # 下：包住原函数，Command 注册包装后的协程
  async def cmd_x(self, stream_id="", **kwargs): ...
  ```

### 31. `webui.json` 格式错了会把整个 WebUI 不可用

- 问题：按旧版格式写 `webui.json`（`webui_version: 1` + `title` + `sections`），直接部署上线。
- 表现：插件注册失败 → **整个 WebUI 打不开**，不是「只有这个插件没页面」。
- 根因：`WebUIExtension` 是严格模型，要求 `schema_version: 2` + `pages` 数组（1~20 个）。
  旧字段全是非法字段，抛 9 个校验错。
- 规避方式：
  1. 不要急于着写 `webui.json`。**没有这个文件是合法的**——`load_webui_extension()` 直接 `return None`，
     插件照常加载，只是不注册 WebUI 页面。先让插件跑通，UI 后面再加。
  2. 真要写：顶层必须 `schema_version: 2` + `pages`；有 `placement: "workspace"` 的页面就必须有
     `workspace_title`；`custom` 页用 `entry` 指向插件内相对 `.html`（**不能**内联 `document`，
     宿主自己读文件注入）；`custom` 页必须在 `required_capabilities` 声明 `"custom_pages"`。
  3. 参数是严格模型：不能写 `default`，只能 `type` / `required` / `minimum` / `maximum` / `choices`。
  4. 部署前跑 `python tests/check_webui_schema.py`（用真实 schema 校验）。

### 32. 自定义页面的 API 必须在宿主侧注册过

- 问题：`webui.json` 里写了 `"api": "webui_get_overview"`，以为只要方法存在就行。
- 表现：`[E_BAD_PAYLOAD] WebUI 页面 overview 引用了未注册的静态 API: webui_get_overview@1`。
- 根因：页面的 query/action 只能引用**已经向宿主注册的静态 API**，光有同名方法不够。
- 规避方式：要么先用纯 `declarative` 页面（只读配置、不调 API），
  要么先把 API 用 `@API` 装饰器注册好、确认名字与版本对得上，再写进 `webui.json`。

### 33. `llm.generate(task_name=...)` 不是自由标签

- 问题：`ctx.llm.generate(prompt, task_name="huixiang")`，以为 task_name 是给调用方分类用的随便写。
- 表现：`[cap.llm.generate] 执行失败: 未找到名为 huixiang 的模型配置`。
  更隐蔽的是**上层无法察觉**——插件侧只看到返回空字符串，最后报「总结字数不足（0 < 200）」，
  表现为模型输出偏少，实际是一次模型调用都未成功。连续 48 轮都栽在这。
- 根因：`task_name` 必须是 `model_config.toml` 里已声明的 `[model_task_config.XXX]` 段名。
  服务器上现有合法名：`web_search` / `replyer` / `planner` / `memory` / `utils` / `learner` /
  `fast_model` / `emoji` / `vlm` / `voice` / `embedding` / `image_embedding`。
- 规避方式：写内容用 `replyer`；并做多级回退（`replyer → utils → fast_model → planner`），
  避免某一个任务没配模型就把整条链路废掉。另外**宿主可能不抛异常、只回空结果**，
  必须自己对「返回空」显式报错，否则错误信息会指向完全错误的方向。

### 34. 「未知」不能兜底成「0」

- 问题：`LifeTrace.social_battery` 默认 `0.0`，`can_speak_now` 判断 `0 * 100 < 40` → 拦。
- 表现：没接 life-frequency 插件时，社交电量恒为 0，`run_once` 永远返回「当前不宜开口」，
  整条发帖流水线一次都跑不到护栏。
- 根因：把「没读到」和「读到 0」混成一个值。两者语义完全相反。
- 规避方式：默认值用 `None` 表示未知，判定时 `if value is not None and value < threshold`。
  凡是「外部信号 + 阈值判断」的字段，都要先想清楚「缺数据」该怎么处理。

### 35. 模型写不够字数，光加重试次数没用

- 问题：要求 200–400 字，模型每次只给 120 字左右；重试 2 次提示词还跟第一次一模一样。
- 表现：`总结字数不足（120 < 200）`，整条总结链路判失败。
- 根因：两个问题叠加——① 重试提示词没告诉模型「上次差多少」，它自然还是给同样长度；
  ② 模型输出确实偏短时，增加重试次数无法解决。
- 规避方式：① 重试提示词带上「上一版只有 N 字，这次必须写到 M 字以上，多说具体细节」；
  ② 加 `pad_summary_to_min()` 兜底：字数差多少，就用**已刷到的真实标题**铺一段「另外还刷到…」，
  不编造、不重复同一批标题（重复列表读起来最机械）。

### 36. 配置页默认显示的是「属性名」，不是中文

- 问题：`Field(description="是否启用插件")` 写得很认真，以为界面就能看懂。
- 表现：用户点进插件设置，满屏 `enabled` / `mode` / `browse_interval_seconds` /
  `dry_run_no_quota_cost` 这类英文标识符，看不懂也改不了。
- 根因：宿主 `_build_field_schema()` 里 `label = json_extra.get("label") or field_name`，
  **description 只是说明文字，标题取的是 `json_schema_extra["label"]`，没给就退回英文属性名**。
  段标题取 `__ui_label__`，段说明取类 docstring。
- 规避方式：每个字段都写
  `Field(default=..., description=..., json_schema_extra={"label": "中文名", "hint": "中文说明"})`；
  每个配置类都写 `__ui_label__` / `__ui_icon__` / `__ui_order__`；
  写完后跑一遍 `generate_plugin_config_schema()`，检查有没有 `label == field_name` 的漏网字段。

### 37. 下拉选项没有「值 → 中文名」映射，值本身就该写中文

- 问题：`mode: Literal["dry_run", "auto"]`，界面下拉里显示的就是 `dry_run` / `auto`。
- 根因：`_extract_select_choices()` 直接把 Literal 的值当候选返回，宿主没有 i18n 映射表。
- 规避方式：枚举字段改用 `str` + **中文默认值**（`"演练"` / `"自动"`），
  再写一层 `norm_choice()` 把中文值归一化成内部英文值，并兼容老配置里的英文值。
  接入点要全覆盖：运行模式、分区范围、总结触发方式，漏一个就会出现
  「界面选了中文、代码按英文判断」的静默失效。

### 38. 自定义后台页面必须先注册 API

- 问题：webui.json 里写了 `{"api": "hx_overview"}`，但插件里没 `@API` 组件。
- 表现：`[E_BAD_PAYLOAD] WebUI 页面 xxx 引用了未注册的静态 API: hx_overview@1`。
- 根因：页面的 query/action 只能引用**已向宿主注册**的 API 组件，光有同名方法不算。
- 规避方式：
  1. 先在插件类里 `@API(name="hx_overview", version="1")` 注册方法；
  2. webui.json 里按**完全相同的名字**引用；
  3. HTML 里用 `await maibot.query('overview')` / `await maibot.action('browse_now', {})`
     （这里的名字是 webui.json 里 queries/actions 的**键名**，不是 API 名）；
  4. 跑 `tests/simulate_runner_load.py`，它会自动比对「页面引用的 API」与「已注册组件」。

### 39. 有固定选项的字段，避免用户手打

- 问题：`trigger_by: str = "按帖数"`，界面上是文本框，用户得自己打「按帖数」「两者都看」，
  打错一个字（「按贴数」「两者都算」）就静默失效，而且没有任何报错。
- 根因：以为「值写成中文」就完事了，没意识到 `str` 类型在宿主里渲染成文本框，
  `choices` 为空，前端就不画下拉。
- 规避方式：用 `Literal["按帖数", "按时间", "两者都看"]`。
  宿主 `_extract_select_choices()` 会把 Literal 值提取成 `choices`，
  前端 `if (n.type === "select" && n.choices)` 就渲染成 Select；
  pydantic 同时只接受这几个值，用户不可能打错。
  老配置里的英文值用 `@field_validator(mode="before")` 静默转换，避免历史配置加载失败。

### 40. 动态选项（分区/社区）要覆盖 `get_webui_config_schema()`

- 问题：分区是运行时从接口拉的，但配置 schema 是静态生成的，
  `Literal` 硬编码就会过期，`str` 又只是文本框。
- 根因：`build_config_schema()` 只看类型注解，没有运行时回调。
- 规避方式：基类 `get_webui_config_schema()` 是**允许覆盖的实例方法**
  （Runner 的 `_get_plugin_config_schema` 调的就是实例），在里面：
  1. 先 `super()` 拿完整 schema（含所有中文 label）；
  2. 从本地缓存读真实分区名（**只读缓存，别在生成 schema 时发网络请求**）；
  3. 给目标字段设 `type="select"` + `ui_type="select"` + `choices=[...]`；
  4. 列表为空时保留原文本框，避免用户卡在空下拉。
- 注意前端 `Select` 不接受空字符串做选项值，「不指定分区」要用中文哨兵，
  业务侧再归一化成空串。

### 41. 后台要能自己显示登录状态和二维码

- 问题：登录只做了 QQ 命令（`/回响登录`），后台面板看不到登没登录，也没法扫码。
- 根因：把「扫码」当成了纯聊天侧交互。
- 规避方式：后台加登录卡片 + 两个 API（状态轮询 / 生成二维码）：
  - 未登录 → **页面打开就自动生成二维码**并展示，不要让用户先点按钮；
  - 二维码用 `data:image/png;base64,...`，前端直接 `<img src>`；
  - 页面定时轮询，扫码确认后自动切成「已登录」并展示昵称 + 账号尾号；
  - **凭据绝不返回前端**，只给昵称和 uid 尾号；过期支持一键重生成。

### 42. 后台页面一次最多只能有 2 个在飞的请求

- 问题：页面用 `Promise.all` 一次发 4 个查询（总览 / 记录 / 分区 / 登录）。
- 表现：进后台一直转「读取中」，状态区全空，手动操作报
  `Two requests are already running`。
- 根因：`plugin-webui-C1enjH3M.js` 的 bridge 硬编码
  `if (pending.size >= 2) throw new Error('Two requests are already running')`。
  4 个并发 + 10 秒自动刷新 + 未登录自动弹二维码，必撞上限；
  而且用 `Promise.all` 时**一个失败整批失败**，页面就一直卡在初始态。
- 规避方式：
  1. 加全局串行队列，所有 `query` / `action` 都排队，任何时刻只有 1 个在飞；
  2. 多个查询严格 `for ... await`，每个单独 try/catch，一个失败不拖垮整页；
  3. 双锁：`refreshInFlight` 挡自动刷新堆叠，`busy` 挡手动按钮与自动刷新互抢；
     内部刷新要用不带 `busy` 判断的 `_refreshNow()`，否则会自己锁死自己；
  4. 自动弹二维码这类「刷新里再发请求」的动作复用外层锁，避免重复加锁。
- 另外：自定义页面的 HTML 是**注册时固化在宿主内存里的快照**（document 接口返回 snapshot），
  改完 HTML 必须**重启 MaiBot** 才会生效，光传文件没用。

### 43. 后台页面会触发宿主「主题字体不可用」红字

- 问题：进插件后台，页面顶部弹 `Error: Theme font unavailable: JetBrainsMono-Medium.ttf`。
- 排查：字体文件本身是好的、HTTP 200 也能下下来。**不是插件的问题**，是宿主
  `plugin-webui-C1enjH3M.js` 的边界 bug：它把页面计算样式拼成一段 CSS 字符串，
  用 `t.includes(字体名)` 判断要不要 `fetch('/fonts/xxx')`；
  沙箱 iframe / 反代 / 非标准端口下这个相对路径可能 404，失败又直接渲染到外层页面顶部。
- 规避方式：不要改宿主源码（升级会覆盖）。在插件页面里：
  1. 用 `!important` 把 `html/body/button/...` 和宿主探针选择器
     （`[data-theme-probe]`、`.maibot-card`、`.maibot-button` 等）全量覆盖成系统字体栈；
  2. 覆盖 `--typography-font-family-code` / `--mil-font-pixel` / `--retro-font-heading` 变量；
  3. **CSS 注释里也不能出现那几个字体名**——宿主扫的是整段样式字符串，注释也算；
  4. 加 `error` / `unhandledrejection` 兜底静默这类噪声。
- 顺带：判断「是不是我方问题」时先探 HTTP 状态、验文件头，不要急于着改自己的代码。

### 44. 可选装饰数据获取失败，避免它拖垮主流程

- 问题：感想总结第一步就去真实请求分区目录（`TOPIC_INDEX`），上游偶发拒绝抛
  `CommentRejectedError`，整轮总结直接记 `执行异常`，明明 LLM 和发帖都没问题。
- 根因：把「分区」这种**可选装饰**放在了关键路径上，而且没兜异常。
- 规避方式：
  1. 凡是「获取失败也能干」的数据，调用处一律 try/except 捕获处理，回落本地缓存；
  2. 缓存也没有就返回 `None`，让后续逻辑走「不挂分区」分支；
  3. 日志用 warning 记原因，不要把异常名透给用户看。
  4. 写回归测试：mock 上游抛错，断言主流程仍能返回正常结果。
- 同理适用于浏览、互动、总结三个入口，不应仅修报错的那一个。

### 45. 「看状态」的后台 ≠ 用户心里的「后台」

- 问题：做了个只显示状态 + 手动按钮的「后台管理」，改配置却要跳到宿主的
  「插件管理」页。用户直接问「是不是两个页面放反了」。
- 根因：按技术分层（宿主配置 vs 插件自定义页）设计，不是按用户心智设计的。
  用户点进「后台管理」就是**要改配置**，不会接受「请去别处改」。
- 规避方式：把配置能力直接放进后台管理页。
  - 宿主的配置写入接口（`PUT /api/webui/plugins/config/{id}`）在**沙箱 iframe 里调不了**，
    要走插件自己的 `@API`；
  - 调用 `get_webui_config_schema()` 拿宿主生成的中文表单定义来渲染，
    不应自行再写一套，避免两边字段/下拉不一致；
  - 写 `config.toml` 用 `tomlkit` 保留注释和 `[plugin]` 段位置，写前备份；
  - 保存后 `set_plugin_config()` 热更新，不用重启；
  - 和宿主配置页读写同一份文件，两边天然同步。
- 另外：返回「N 条数据」时，列表条目数要和 N 对得上；
  过滤掉无标题的就明说「N 条中 M 条有标题」，避免用户以为被吞了。

### 46. WebUI 的 `object` 参数不能传动态字典

- 问题：`webui.json` 里声明 `"sections": {"type": "object", "required": true}`，
  页面把整个配置字典传过去，点保存报 `ApiError: 参数不符合声明: sections`。
- 根因：`webui_schema.Parameter.accepts()` 对 object 的判定是
  `not value.keys() - self.properties.keys()` —— 必须**先声明所有允许的键**，
  且只接受这些键。配置段是动态的，没法穷举，所以传任何非空字典都失败。
- 规避方式：动态结构一律用 **JSON 字符串**传
  （`{"type": "string", "required": true, "max_length": 60000}`），
  前端 `JSON.stringify`，后端 `json.loads` 并做格式错误的中文提示。
  只有结构完全固定的参数才用 object + properties。

### 47. 提示要「看得见」，页面要「收得起」

- 问题：把字段说明写入 `title` 属性，以为用户会悬停；用户直接说
  「我后台设置你不给我提示我怎么知道怎么配啊」。另外一口气铺 7 个卡片，
  信息太满，用户说「不要那么多信息」。
- 规避方式：
  1. 每个配置项的中文 hint **直接渲染成可见小字**，放在标签和输入框之间；
  2. 主功能（配置）默认展开，次要信息收进默认折叠的「其它」区；
  3. 折叠区标题栏放一行状态摘要，收起来也能看到关键信息；
  4. 折叠状态存 localStorage，刷新不复位；
  5. 删掉「怎么改设置」这类重复说明块。
- 顺带：用户说「插件页面」时，在 MaiBot 语境里指的是**插件扩展里的自定义页面**，
  不是 WebUI 本体。需确认改动对象准确。

### 48. 表单保存前必须按模型校验，否则会引发「页面下线」连锁反应

- 问题：后台保存配置，页面报 `ApiError: 插件 WebUI 已下线`。
  看日志才发现是一串：
  `多选字段写成字符串 → 文件写成功但 pydantic 校验失败 → 宿主 file_watcher
  检测文件变动自动重载插件 → 旧页面注册句柄失效`。
- 根因：① 前端把 `multiple` 的 select 当单选字符串存；
  ② 后端先写文件再校验，坏配置已经落盘；③ 宿主监听 config.toml 变动会自动重载。
- 规避方式：
  1. 多选字段用 `<select multiple>`，保存时 `Array.from(selectedOptions)` 成数组；
  2. **写文件之前**先 `ConfigModel.model_validate(merged)`，不合法整单拒绝、文件零改动；
  3. 页面遇到「已下线 / unavailable」时给中文提示并延时自动重连，
     避免用户误判为插件故障（宿主重载是框架行为，改不了也不该改）。

### 49. 自动刷新不能覆盖用户正在编辑、还没保存的表单

- 问题：用户「刚想把演练改成自动」，10 秒定时器把刚选的值刷回旧值。
- 根因：定时刷新无条件重绘整个表单，没有「未保存改动」概念。
- 规避方式：加 `dirty` 标记，字段 `input`/`change` 即置位；
  dirty 时**只更新缓存不重绘 DOM**，暂停自动刷新并显示「有未保存的修改」；
  保存成功 / 主动「重新读取」后清除标记恢复。

### 50. 选项很多的多选字段不使用 `<select multiple>`

- 问题：分区多选有 94 项，用 `<select multiple size="5">`，用户反馈「下拉框全都失效了」。
- 根因：数据没问题（API 返回 94 个 choices），是**交互**坏了——
  在沙箱 iframe 里要按 Ctrl 才能多选，94 项压缩在 5 行里，看着就像点了无响应。
- 规避方式：选项超过十几个的多选字段，一律用
  **搜索框 + 复选框列表 + 全选/清空 + 已选计数**；
  双列平铺、限高滚动，保存时从所有 checked 收集成数组。
  单选下拉才用 `<select>`。
- 排查这类「失效」时先分清是**数据没到**还是**交互不可用**——
  本次接口返回完全正常，修改数据层无效。

### 51. 只传 `task_name` 选不到你想要的那个模型

- 问题：用户要求「用 GM 不使用 DeepSeek」，改了配置也没用，生成出来还是 DeepSeek。
- 根因：宿主 `model_config.toml` 里 `[model_task_config.replyer]` 的
  `model_list = ["ds-official", "feiyu-gemini-flash"]`，**按顺序取首个**。
  插件只传 `task_name="replyer"`，模型选择权完全在宿主配置里，插件插不上手。
- 规避方式：要指定具体模型就用 `llm.generate(..., model_name="xxx")`。
  SDK 契约写明「传 `model_name` 一律直选具体模型，即使它与任务同名」，
  这是唯一能绕过任务优先级顺序的口子。模型名必须是 `model_config.toml`
  里 `[models]` 的 `name`（不是 `model_identifier`），写错会静默回落到默认。
- 验证方式：看宿主日志 `选择请求模型: xxx (策略: sequential)` 和
  `Token使用情况 - 模型: xxx, 类型: plugin.<插件ID>`，不应仅看自己的配置。

### 52. 宿主 `cap.call` 默认只等 30 秒，长文本生成必超时

- 问题：写 200~400 字的帖子频繁失败，日志 `[E_TIMEOUT] 请求 cap.call 超时 (30000ms)`，
  上层只看到「生成失败」，用户看到的是「点了无响应」。
- 根因：`llm.generate` 走 RPC，默认等待预算 30000ms，长文本经常跑不完。
- 规避方式：显式传 `timeout_ms=180000`（SDK 支持，会被当成这次
  cap.call 的等待预算，life-frequency 插件同款用法）。
  外层再套 `asyncio.wait_for` 捕获处理，避免 RPC 卡死整轮。

### 53. 「建议重写」缺少执行方即无实际作用

- 问题：护栏判「文字太像机器（AI 味 62 ≥ 60），建议重写」，用户等着它重写，
  结果始终未触发重写，下一轮仍生成新内容。
- 根因：护栏只**返回**失败结果，调用方 `if not verdict.ok: return 失败`，
  **全代码库没有一处真的去重写**。「建议」写在了 message 里，但没人读它。
- 规避方式：凡是 message 里出现「建议 / 请 / 应该」这类动作词，
  回头确认**有没有代码真的执行这个动作**。重写要闭环：
  把上一版正文 + 具体改进要求塞回提示词重新生成，并设轮数上限。
  同时区分「重写有用的失败」（AI 味、字数不够）和「重写没用的失败」
  （额度、间隔、去重、时段）——后者必须立即返回，避免无效的模型调用。

### 54. 模式（演练/自动）不能只在启动时定一次

- 问题：后台把「演练」改成「自动」，操作记录里还是 `[dry_run]`；
  过一阵又冒出 `[real]`，看着像「一会儿自动一会儿演练」。
- 根因：worker 的 `mode` 在 `__init__` 固化；改配置后靠
  `asyncio.create_task` 异步重建，没有事件循环时抛 `RuntimeError`，
  异常被吞 → 旧 worker 带着过期的 `DRY_RUN` 继续跑。
- 规避方式：worker **每轮开头**按当前配置重新判定一次 mode
  （`_current_mode()`），不依赖重建成功；重建失败只影响日志，不影响正确性。
  另外「保存配置」这类记录别硬编码 `mode=DRY_RUN`，写实际模式。

### 55. 「额度用完了」和「功能坏了」看起来一模一样

- 问题：用户以为插件不工作，实际是当日 3 条额度早用完了，每轮都在
  `quota_exhausted` 失败。
- 根因：状态页只显示「真实已用 4 次」，未给出上限，无法判断 4 ≥ 3。
- 规避方式：额度一律显示 `已用 / 上限`，达到上限时在页面上高亮提示
  「今天的真实发帖额度已用完，明天自动重置，或到安全护栏调高上限」。
  排障时先看 `quota.json` 和 `[real]/[dry_run]` 标签，不要优先怀疑代码逻辑。

### 56. 公开仓库中不得出现部署环境信息

- 问题：仓库为公开状态时，变更记录与源码注释中包含部署服务器的公网地址、
  绝对路径与账号昵称。此类信息一经提交即进入 Git 历史，即使后续修改文件，
  历史提交仍可被检索。
- 表现：仓库公开期间，上述信息对任何访问者可读。
- 根因：编写技术文档时把「在哪里验证的」当作正常上下文记录，
  未区分「内部运维记录」与「可公开的技术文档」。
- 规避方式：
  1. 文档中一律使用中性表述（如「部署环境」「部署目录」），
     不写具体地址、路径、账号；
  2. 提交前执行脱敏扫描：公网 IP、盘符路径、账号昵称、口令、令牌；
  3. 新建仓库默认设为私有，确认内容可公开后再调整可见性；
  4. 若敏感信息已进入历史，仅修改文件无效，需重建仓库历史
     （删除仓库后重新初始化，或使用历史重写工具），并立即将仓库转为私有。

后续每完成一个模块，回查本表。出现新问题按同样四段格式补充。
